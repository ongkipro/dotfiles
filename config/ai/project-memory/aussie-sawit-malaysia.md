**Shipping/fulfillment: EasyParcel integration** (Malaysian courier aggregator, Open API **2026-06**). The contract is **already verified** from the official repo `easyparcel/OpenAPI` (`source/includes/2026-06/`) → documented in `docs/EASYPARCEL.md` (source of truth). Important verified facts: OAuth2 auth **authorization_code** (authorize once via `/oauth/login`, the token endpoint uses Basic auth, store `refresh_token`+`access_token` in **KV `TOKEN_CACHE`**); booking path **`/shipment/submit_orders`** (plural); cancel `/shipment/cancel` (`cancel_list[{shipment_number,remark}]`); tracking `/shipment/tracking_status` (`{awb_numbers:[]}`, status codes 0/2/3/4/5/6/7/8/11); wallet `GET /wallet`. **1 vendor question remaining:** webhook signature (the spec has NO signature → mitigation: webhook at a secret path `/api/webhooks/easyparcel/:token` + `EASYPARCEL_WEBHOOK_TOKEN` + idempotency + re-verify via tracking_status). **Wallet auto-debit is NOT an issue** (user decision): the flow = customer orders on our platform → our dashboard → we push the booking to EasyParcel; the booking deducts from our prepaid wallet (keep a balance + top-up SOP + alert). **EasyParcel has NO frontend widget/gateway** (server-to-server API): shipping cost to the form via our server proxy `/api/shipping/rates`; the address (postcode→state/city) comes from our MY postcode dataset, not EasyParcel (quotations actually DEMAND postcode+subdivision_code from us). Optional street-address autocomplete uses Google Places etc.

**SHIPPING-COST DECISION v2 (final, replaces the old seller-absorbed assumption):** shipping **is charged to the customer, LIVE-RATE at checkout** (ADR-0009).
