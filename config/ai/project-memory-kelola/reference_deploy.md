**⚠️ READ FIRST — `git push origin main` ALREADY AUTO-DEPLOYS. Do NOT manually deploy after a push.** `.github/workflows/deploy.yml` triggers on push to `main` and runs `bash deploy/deploy.sh` on a **self-hosted runner that IS the production server**. So every push you make kicks off a CI deploy on its own. Running a manual `ssh … bash deploy.sh` on top of it just creates a redundant SECOND deploy (flock-serialized, so they queue — not corrupt — but wasteful). **Discovered 2026-06-07 after chasing phantom 500s for several turns:** the "partial `.next` → all routes 500" I kept seeing was almost always me `curl`-checking the site DURING the CI deploy's build window (web briefly down / `.next` mid-rebuild); it self-heals the moment CI finishes. Worse, manual un-flocked `rm -rf .next && npm run build` RACED the CI build on the same `.next` → that's what produced `ENOENT _ssgManifest.js`. **Correct workflow now: push, then just WAIT for the CI deploy to finish and verify — don't manually deploy or manually rebuild.** To watch it: `ssh … 'pgrep -af "next build|deploy/deploy.sh"'` (empty = CI done), then curl the site.

Manual deploy (only when NOT pushing — e.g. re-running a stuck deploy) is a one-liner:

```
ssh irwansyah10@103.93.161.104 'cd ~/kelola && bash deploy.sh'
```

`deploy.sh` (at repo root) handles everything:
1. `git fetch && git reset --hard origin/main`
2. `npm ci` in backend
3. `npm run db:migrate` (drizzle-kit migrate)
4. `npm ci` in web
5. `npm run build` (Next.js production build)
6. `pm2 reload ecosystem.config.cjs`

PM2 services running on the server:
- `kelola-backend` (Hono API on :3101)
- `kelola-web` (Next.js on :3100)

Nginx in front. **Primary production domain is now `kelolatim.com`** (seen 2026-06-09) → routes `/api/*` to backend, everything else to web. The old `kelola.simantep.id` now 301-redirects to `kelolatim.com` (so a curl to the old domain returns 301, not 200 — that's expected, not an outage). **Verify deploys against `https://kelolatim.com/` and `/sign-in`** (200 = healthy); backend health: `curl http://localhost:3101/api/public/site-verification` (200).

Backend env is at `~/kelola/backend/.env` on server (NOT in git). Holds: `DATABASE_URL`, `BETTER_AUTH_SECRET`, `ENCRYPTION_KEY`, `GOOGLE_CLIENT_ID/SECRET`, `SUPER_ADMIN_EMAILS`, `GPG_RECIPIENT`, `BETTER_AUTH_URL`, `TRUSTED_ORIGIN`, `EXTRA_TRUSTED_ORIGINS`.

**Login broken after domain move — `BETTER_AUTH_URL` must match live domain (fixed 2026-06-10):** symptom "kok tidak bisa login" (esp. Google sign-in). Root cause: `BETTER_AUTH_URL` was still `https://kelola.simantep.id` (old domain) while users are on `kelolatim.com`. Better Auth builds the Google OAuth `redirect_uri` (and email verify/reset links) from `BETTER_AUTH_URL` → callback landed on the old domain (which 301s), so the OAuth state cookie set on kelolatim.com didn't match → login failed. Fix: set `BETTER_AUTH_URL=https://kelolatim.com` in `backend/.env` + `pm2 restart kelola-backend` (no rebuild; .env is gitignored so it persists across deploys). Verify: `curl -sX POST https://kelolatim.com/api/auth/sign-in/social -H 'Content-Type: application/json' -d '{"provider":"google","callbackURL":"/app"}' -D - | grep -o 'redirect_uri=[^&]*'` → must show kelolatim.com. NOTE: Google Cloud Console OAuth client must also list `https://kelolatim.com/api/auth/callback/google` in Authorized redirect URIs, else Google returns `redirect_uri_mismatch`. `TRUSTED_ORIGIN=https://kelolatim.com`, `EXTRA_TRUSTED_ORIGINS` includes www + old domain. Web build uses empty `NEXT_PUBLIC_API_BASE` (relative → same-origin kelolatim.com), so app API calls + cookies are same-origin (password/OTP login unaffected; only OAuth/email-link depend on BETTER_AUTH_URL).

**Flaky `npm ci` on deploy:** backend `npm ci` is flaky and usually succeeds on a plain re-run of `deploy.sh`. Seen transient failures: (1) `ETXTBSY` on the esbuild binary (text-file-busy); (2) native build failure compiling `better-sqlite3`/sqlite3.o (`make ... Error 2`, likely OOM during compile). Both → just re-run deploy. If a partial/interrupted install corrupts `node_modules` (e.g. `ERR_MODULE_NOT_FOUND` for `tsx/dist/package-*.mjs` at the `db:migrate` step), fix with a clean reinstall: `ssh … 'cd ~/kelola/backend && rm -rf node_modules && npm ci'` then re-run deploy. Rule of thumb: retry deploy 1–2× before digging in.

**All routes 500 after deploy — partial `.next` (`middleware-manifest.json` / `_ssgManifest.js` missing) (seen 2026-06-07, hit ~4× before real cause found):** `next start` 500s on every route (incl `/sign-in`) when `.next` is incomplete. Confirm with `ls ~/kelola/web/.next/server/middleware-manifest.json` (missing = this bug). **REAL root cause:** the still-running `next start` (kelola-web) process accesses `.next` *while* `next build` writes it → race → build dies at "Finalizing page optimization" with `ENOENT … _ssgManifest.js` (or leaves middleware-manifest unemitted). Intermittent → why manual `rm -rf .next && npm run build` sometimes "worked" (web happened not to race) and sometimes also failed. NOT just stale-.next. **Fixed in `deploy.sh` (committed 2026-06-07):** step [5/6] now `pm2 stop kelola-web` BEFORE build (kills the race), builds from clean `.next` with up-to-3× retry + `middleware-manifest.json` verification (build is flaky under server load), aborts safely if all fail; step [6/6] uses `pm2 startOrReload ecosystem.config.cjs` (starts the stopped web, reloads backend). First clean run compiled in ~28s with no retry. Tradeoff: ~1-2 min web downtime during build — acceptable vs. the old guaranteed-breakage. Manual recovery if ever needed: `ssh … 'pm2 stop kelola-web; cd ~/kelola/web && rm -rf .next && npm run build && pm2 startOrReload ~/kelola/ecosystem.config.cjs'`. NOTE: a `deploy.sh` change only takes effect the deploy AFTER it lands (the running script is the on-disk copy from invocation time); to apply immediately, `git -C ~/kelola fetch && git reset --hard origin/main` first, then run deploy.sh.

**ChunkLoadError / `_next/static/chunks/<hash>.js` 500 on a specific page (seen 2026-06-09, e.g. /app/budget):** the served build's HTML references a chunk file that does NOT exist on disk → `next start` returns 500 for it → `ChunkLoadError` → page stuck "This page couldn't load" / "Memuat…". ROOT CAUSE: **Turbopack (default bundler in Next 16) skips emitting some chunks when its cache is stale** — content-based hashes make it think a chunk is already built, but `rm -rf .next` deleted the actual file while the Turbopack cache in `node_modules/.cache` persisted → output/cache desync. This was TRIGGERED by the earlier `deploy.sh` hardening that added `rm -rf .next` (which clears output but not the turbo cache). **REAL fix (2026-06-11, after it recurred several more times incl a layout chunk `04egw` breaking ALL pages):** the 2026-06-09 verify read `.next/app-build-manifest.json` — but **that file does NOT exist in Next 16 + Turbopack**, so the verify always threw → no-op (deploy "aborted" yet still started web with whatever `.next` was built), letting inconsistent builds ship. New `deploy.sh` step [5/6] verify: `rm -rf .next node_modules/.cache`, then a node scan collecting EVERY `static/chunks/*.js` reference across `.next/server/**` (incl per-route `*_client-reference-manifest.js`) + `build-manifest.json` (rootMainFiles+pages), confirming each file exists; retry build up to 3× if any missing. A healthy build reports `referenced≈118 missing=0`. Manual repair: `ssh … 'pm2 stop kelola-web; cd ~/kelola/web && rm -rf .next node_modules/.cache && npm run build && pm2 startOrReload ~/kelola/ecosystem.config.cjs'`. Verify consistency: fetch the page HTML, extract `/_next/static/chunks/*.js` refs, confirm each exists under `~/kelola/web/.next/`. Client-side mitigation already in place: `web/components/chunk-reload-guard.tsx` auto-reloads once on ChunkLoadError (handles stale open tabs after deploy).

**`ENOTEMPTY: rmdir … node_modules/…` during npm ci (seen 2026-06):** root cause was a **crash-looping pm2 process** holding file handles in `node_modules` while npm ci tried to clean it. Check `pm2 list` — a huge `↺` restart count (e.g. `kelola-web` at 1000+) = crash loop, usually because its own node_modules is already half-broken; npm racing the restarting process → ENOTEMPTY/ENOENT on rmdir. **Fix:** stop the services first, then clean reinstall: `ssh … 'pm2 stop kelola-web kelola-backend; rm -rf ~/kelola/backend/node_modules ~/kelola/web/node_modules; cd ~/kelola && bash deploy.sh'` (deploy.sh's final `pm2 reload` restarts them). **Two gotchas:** (1) do NOT `npm cache clean --force` mid-recovery — it half-deletes the cache → `ENOENT … _cacache/content-v2/…`; if that happens nuke it fully: `rm -rf ~/.npm/_cacache` then reinstall. (2) do NOT `pm2 stop all` — the server also runs `simantep` and `tatacuan-bot` (NOT in kelola's ecosystem.config.cjs), so deploy.sh won't restart them; stop only the two `kelola-*` apps, or `pm2 restart simantep tatacuan-bot` afterward.
