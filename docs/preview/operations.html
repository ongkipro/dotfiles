Bootstrap, verify, recover

Operations & Validation

The operational path is intentionally explicit: inspect the installer, preserve existing files, link canonical sources, run health checks, and keep production or destructive actions behind a human approval boundary.

Install and bootstrap

Linux and macOS use separate entry points but consume the same fail-closed runtime command manifest. Replaced regular files are preserved as timestamped backups before managed links are created.

git clone https://github.com/ongkipro/dotfiles.git ~/dotfiles
cd ~/dotfiles
bash install.sh          # Linux
# bash install-macos.sh  # macOS

Broad helpers such as dotsync commit, dotsync sync, and dotpush are only safe when the entire working tree is intentionally in scope. Mixed trees require explicit path staging.

Cross-device recovery

Pull reviewed changes only from a clean worktree. Synchronization is explicit and never rewrites history automatically.

cd ~/dotfiles
git pull --ff-only
ai-doctor

If branches diverge, fetch and inspect both sides before integration. Force-push, history rewriting, and background push are outside the normal recovery path.

Approval and safety boundaries

  • Secrets: Never track credentials, tokens, auth state, customer data, private keys, or .env files.
  • Destructive actions: Filesystem deletion, destructive migrations, and data loss risks require explicit approval.
  • System and production: System-wide changes, deploys, DNS updates, releases, and remote writes remain human-gated.
  • Scope: Unrelated worktree changes belong to their author; do not absorb them into the current task.
  • Git: Stage only intended paths. Commit and push only when explicitly requested.

Validation and release evidence

bin/ai-doctor --self-test is the authoritative local gate for the dotfiles control plane. It covers memory references, secret scanning, cross-runtime policy, discovered fixtures, OMP routing, and the Git guard. GitHub Actions runs the core suite on Linux and macOS.

A past green check is not current evidence. Each revision must be established from the applicable local command and hosted run; a successful check still does not authorize production deployment.
