# Parallel AI development machine

How `rich` (Dell OptiPlex 7050, Ubuntu 24.04) runs several AI terminals across several projects, and how to reproduce
the same setup on another Linux or macOS device. Evidence: `docs/research/parallel-ai-dev-machine-2026-11-07.md`
(public sources, each labelled as official, forum, blog or vendor; none of them is a controlled study).

This page separates three kinds of statements: **[measured]** on `rich`, **[sourced]** from the research note, and
**[assumption]** by the author. Do not read an assumption as a rule.

## 1. Reference profile (`rich`) [measured 2026-11-07]

| Part | Value | Consequence |
|---|---|---|
| CPU | i7-7700T, 4 cores / 8 threads, 35 W | Heavy jobs (build, full suite, browser) are CPU-bound: two at a time |
| RAM | 32 GB, about 19 GB available with four agents | Memory was not the limit |
| SSD | 240 GB SATA without DRAM, 63% used | Slows down when nearly full; keep below about 75% |
| HDD | 1 TB at `/data` | Archives and backups only, never builds or databases |
| Swap | zram 7.8 GB (priority 100) plus swapfile | Compressed RAM first, SSD last |

Other devices differ. Do not copy numbers; run `ai-capacity measure` and `ai-capacity apply` on each device.

## 2. What is installed and where it lives

| Concern | Tool | Tracked at | Applied by |
|---|---|---|---|
| Queue and cap for heavy jobs | `heavy-run` (pool slots, named locks, systemd scope) | `bin/heavy-run` | linked into `~/.local/bin` by `install.sh` from `config/ai/runtime-commands.txt` |
| Per-device sizing | `ai-capacity` (plan, measure, apply, status) | `bin/ai-capacity` | `ai-capacity apply` writes device-local files |
| Throwaway test databases in RAM | `ai-testdb` | `bin/ai-testdb` | on demand |
| Pre-maintenance snapshot | `dev-freeze` | `bin/dev-freeze` | on demand |
| Memory pressure rules | `ai-heavy.slice` | generated by `ai-capacity apply` into `~/.config/systemd/user/` | `systemctl --user daemon-reload` |
| Tool versions | `mise` | `config/mise-config.toml` | `mise install` |

Device-local, never tracked: `~/.config/ai-local/capacity.env`, `capacity-costs.json`, the slice unit, the pi-subagents
limits. Each device sizes itself.

## 3. Rules that make parallel work fast

1. **One agent, one worktree, one branch.** Worktrees isolate code only; ports, databases and caches stay shared
   unless you isolate them too [sourced: research note A1, A8].
2. **Shorten heavy work before adding slots.** Per task run only the tests for the changed code; run the full suite once
   per milestone or on merge; cap round trips to CI [sourced: A3]. A queue lock only turns collisions into waiting.
3. **Isolate the runtime per job.** A private database per run (`ai-testdb run <name> --from <template> -- <cmd>`) removes
   the need to queue for a shared test database [sourced: A1, A5]. A clone isolates the database only: keep a
   repository lock while runs still share a build directory, a server, ports or temp files.
4. **Keep time-sensitive tests out of the per-change run** and run them once per release on a quiet machine [sourced: A1].
5. **Watch pressure, not usage.** `/proc/pressure/{cpu,memory,io}` (Linux 4.20 or newer) shows how long tasks wait;
   a sustained `full` above zero means the machine is stalled [sourced: A7].
6. **Queue everything heavy through `heavy-run`**, with `--lock <repo>-env` while a repository's runs share one server
   or database. Never poll: start in the background and wait for the completion notice.

How many agents? Public guidance puts the sweet spot at three to five and names review capacity and plan quota, not
CPU, as the first limit [sourced: A2]. `rich` runs four. How many heavy jobs? Two on four cores [measured]; whether
a third helps on a bigger CPU is not established.

## 4. Reproduce on another Linux device

1. `install.sh`, then `mise install` (tools come from `config/mise-config.toml`).
2. Check that `heavy-run`, `ai-capacity`, `ai-testdb` and `dev-freeze` are on PATH: `install.sh` links every command listed in `config/ai/runtime-commands.txt` into `~/.local/bin`. (`ai-memory-link` only renders and links the AI context.)
3. Run the agents for a while, then `ai-capacity measure` and `ai-capacity apply`; read its output: it says which limits
   are enforced and which are only targets. A device with too little memory is reported as degraded and nothing is applied
   without `--force`.
4. Optional, needs sudo and your decision: `systemd-zram-generator` and the `bfq` scheduler for a SATA SSD (see
   `docs/linux-maintenance-log.md`). Both are reversible; neither is required.
5. Before maintenance or a long pause: `DEV_FREEZE_ROOT=$HOME/.local/state/dev-freeze dev-freeze` (the default output,
   `/data/backups`, is this reference machine's layout and fails on a device without that directory), and ask running
   terminals to checkpoint their notes. A snapshot copies untracked files as they are, so it can contain `.env` files and
   keys: keep it private, never commit or share it, and delete old snapshots.

## 5. Reproduce on macOS

**Not supported as shipped; not verified on a Mac.** macOS has no systemd, cgroups, `/proc` or zram, and two of the
helpers depend on Linux behaviour today:

- `heavy-run`: without `systemd-run` it automatically skips systemd scoping (`AI_HEAVY_NO_SCOPE=1` disables scoping
  explicitly), but its cleanup of leftover processes after a job reads `/proc` and uses `os.waitid`, which has no
  non-Linux fallback. Treat it as Linux-only until that is ported and tested.
- `dev-freeze`: uses Bash associative arrays (Bash 4 or newer; the Bash that ships with macOS is 3.2), `date -Iseconds`
  and other GNU options. It needs a newer Bash and GNU coreutils, or a port.

What does carry over: the git rules and worktree-per-task, `mise` and its tools (installed by `install-macos.sh`, see
[`macos-install-step-by-step.md`](macos-install-step-by-step.md)), `ai-testdb` where Docker is installed (not verified),
and the research and scraping rules. The memory cap, PSI and zram parts have no macOS equivalent, and `ai-capacity apply`
reports the cap as not enforced there. Functional macOS parity is a separate piece of work with its own tests.

## 6. Research, scraping and parallel browsing

The rules live in `config/ai/memory/parallel-research.md` (loaded on demand by the memory router). In short: parallel
research agents are read-only, official APIs and documents come before scraping, and scraping is polite, bounded,
logged and never touches personal data without an explicit owner decision. Those scraping defaults are a proposal until
the owner confirms them.

## 7. Backups of development databases

Development volumes can hold real data. `rich-db backup` writes verified dumps to `/data/backups/postgres/` on a timer.
That copy is on the same machine; a copy that leaves the machine (restic or rclone to object storage) is not set up and
needs an owner decision on destination and retention [sourced: A6]. Test a restore periodically; an untested backup is
an assumption.

## 8. Verify

```bash
heavy-run --status
ai-capacity status
cat /proc/pressure/cpu /proc/pressure/memory /proc/pressure/io
swapon --show; cat /sys/block/sda/queue/scheduler
bin/heavy-run-test && bin/ai-capacity-test && bin/ai-testdb-test && bin/dev-freeze-test
```

## 9. Known gaps (as of 2026-11-07)

- `heavy-run` does not record queue wait time, so "how long do agents wait" is still an assumption.
- No project uses `ai-testdb` yet; port and compose-project isolation per worktree does not exist.
- `ai-capacity status` does not read PSI yet.
- Off-machine backup, and macOS verification, are open.
