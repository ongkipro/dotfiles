# Data design and invariant choices

Use this reference after stating the invariant in business language. The Drizzle schema
should express the intended PostgreSQL object; generated SQL must still be reviewed.
Retrieve current Drizzle column, constraint, index, and relation APIs for the installed
version before coding.

## Keys and relationships

- Prefer a stable, meaningless primary key when business identifiers may change. A
  natural key can remain `UNIQUE` when it is a real invariant.
- Decide whether identity is generated by PostgreSQL or supplied by the application.
  Avoid two competing generators or silently mutable keys.
- A foreign key protects existence, not tenant equivalence. In shared-table tenancy,
  include `tenant_id` in child identity/reference paths and use a matching composite
  unique/primary key plus composite FK where cross-tenant references must be impossible.
- Choose `ON DELETE`/`ON UPDATE` behavior explicitly. `CASCADE` is correct only when the
  child has no independent lifecycle; `RESTRICT`/`NO ACTION`, `SET NULL`, and `SET
  DEFAULT` each imply different product behavior.
- Use deferrable constraints only for a demonstrated multi-step invariant that cannot be
  ordered normally. Confirm Drizzle and migration support from current documentation;
  explicit SQL is preferable to pretending unsupported schema DSL is portable.

## Nullability, uniqueness, checks, defaults

- `NOT NULL` means absence is invalid. Do not use an empty string, zero, `{}`, or a magic
  timestamp as a substitute for an explicit optional state.
- PostgreSQL unique constraints normally permit multiple nulls. If “missing” values must
  collide, choose an explicit design such as `NULLS NOT DISTINCT` when supported by the
  installed PostgreSQL version, or a reviewed expression/partial index.
- Scope business uniqueness correctly: many SaaS invariants are unique per tenant, not
  globally. Decide case, whitespace, collation, and soft-delete semantics before choosing
  the indexed expression or partial predicate.
- A `CHECK` passes when its expression is true or null. Pair it with `NOT NULL` when null
  must fail. PostgreSQL assumes a check condition stays consistent for the same row;
  avoid volatile or external lookups. Cross-row/cross-table rules belong in keys, unique
  constraints, exclusion constraints, or transactional logic.
- Put a default in PostgreSQL when every writer should receive it. A default does not
  backfill semantic history and does not make a nullable column required.
- Generated columns are appropriate for row-local derivations that PostgreSQL can
  express and maintain. Retrieve current server restrictions before relying on them.

## Closed values and lifecycle

Choose among:

- `CHECK`: a small closed set changed through schema deployment;
- PostgreSQL enum: strongly closed and readable, but lifecycle operations are deployment
  coupled and must be checked against the target version;
- lookup table + FK: values carry mutable metadata, ordering, localization, or operator
  administration;
- unconstrained text: only when arbitrary values are genuinely valid.

A list of allowed states does not enforce allowed transitions. If a transition depends
on the current row, use a guarded atomic update and test its affected-row behavior. If it
spans rows, define one transaction and the concurrency anomaly it prevents.

## Time

- Store an instant as `timestamptz`; PostgreSQL normalizes it and displays it in the
  session timezone. Preserve a separate IANA timezone identifier when future local-time
  recurrence or the user's civil-time context matters.
- Use `date` for a calendar day with no time, and `time` only for a wall-clock value with
  a separately defined timezone/calendar context.
- `timestamp without time zone` is a local/civil timestamp, not a safe shortcut for UTC.
- Define precision, inclusive/exclusive boundaries, and who supplies created/updated
  timestamps. Database and application clocks are separate authorities.

## Money and numeric values

- Never use floating point for exact money. Use integer minor units only when the
  currency/asset exponent and range are explicit, or `numeric(precision, scale)` with
  stated rounding rules.
- Store currency alongside amount when more than one currency is possible. An amount is
  not meaningful without currency, tax/discount semantics, and whether it is estimated
  or final.
- Do not assume every currency has two decimal places or that historical conversion can
  be recomputed from today's exchange rate.
- Decide whether Drizzle returns numeric values as strings or another representation for
  the installed driver; do not coerce beyond JavaScript's safe numeric behavior.

## JSON and arrays

Use relational columns when a field is constrained, joined, sorted, filtered, unique,
referenced, or independently updated. Use `jsonb` for variable documents whose shape and
query needs are explicit.

For each JSON column define:

- schema/version and validation owner;
- required/optional keys and distinction among SQL `NULL`, JSON `null`, and missing key;
- maximum practical size and update pattern;
- indexes derived from real operators/paths;
- migration strategy when document shape changes.

Do not hide tenant IDs, money, lifecycle state, or referential keys inside JSON merely to
avoid a migration. Arrays are suitable for bounded atomic values, not as a substitute
for a relationship that needs integrity or independent querying.

## Drizzle representation review

Before accepting a schema change, compare the intended PostgreSQL object with generated
SQL. Confirm names, native types, precision/scale, defaults, identity behavior,
nullability, constraint/index predicates, operator classes, sort/null order, FK actions,
and schema qualification. Drizzle relations improve query typing; they do not create a
PostgreSQL foreign key unless the generated DDL does so.
